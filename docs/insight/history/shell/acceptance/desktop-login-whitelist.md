# 桌面登录白名单：本地 dev 验收

适用范围：Shell 的账号请求头、短信发码和短信登录拒绝处理。初次接入时服务端仅发布至测试环境；2026-10-16 操作者确认已同步生产。本清单仍使用连接测试环境的源码 dev 模式，不使用安装包。Core、插件、管理端逻辑不在本次改造范围内。

## 1. 启动当前 Shell

在 Shell 仓库执行：

```bash
cd /Users/boxser.shi/Documents/harness/insight-desktop-shell
npm run dev
```

建议先用 `node --version` 确认 Node 24.x，与发布 CI 一致；Node 20 不满足当前开发构建及完整回归所需的运行时 API。

首次使用或依赖尚未安装时先执行 `npm ci`。`npm run dev` 会准备锁定的 Runtime、运行时清单和默认 Profile，再启动 Electron；无需修改或重建 Core、独立插件项目，也无需使用指定本地 Runtime 的 `dev:local`。

确认启动的是“因赛AI Dev”。源码运行时 `app.isPackaged=false`，账号服务固定使用 `https://gapi-test.insight-aigc.com`；不需要修改环境配置。所有打包运行的客户端目前都选择生产认证环境，不能用测试名称的安装包代替本次 dev 验收。

dev 使用独立数据目录和内存认证会话，不保存登录凭证。完整退出 Electron 后重新启动会回到登录页，这是预期行为；仅关闭 macOS 窗口不一定退出进程。测试间可通过账号菜单退出登录，或在启动终端按 `Ctrl+C`，等待退出后重新运行 `npm run dev`。不要并行运行多个 dev 实例。

## 2. 测试环境前置条件

由服务端同学在测试环境准备并确认以下条件，不需要客户端接入任何管理接口：

- 测试账号 A：已存在账号、可接收短信，加入桌面白名单。
- 测试账号 B：已存在账号、可接收短信，不在桌面白名单；密码登录回归还需要有效密码。
- 能配合切换桌面白名单开关，以及临时移除、恢复账号 A 的白名单资格。
- 需要验证“拒绝登录不自动建号”时，另准备一个未注册的受控手机号 C，由服务端核对账号记录；客户端界面不能证明数据库未建号。

请求头中客户端标识的值为 `Desktop`。测试白名单数据所属类型为 `DESKTOP`，两者不可混用。

## 3. 手动验收步骤

每条用例开始前确认处于登录页。发码拒绝用例应从倒计时为 0 的页面开始，避免上一次成功发码的倒计时影响观察。成功登录用例需要勾选用户服务协议与隐私政策。

| 用例 | 服务端条件与操作 | 客户端预期 |
| --- | --- | --- |
| 开关关闭兼容 | 关闭桌面白名单开关；用 B 获取验证码并完成短信登录 | 发码成功后显示 60 秒倒计时；有效验证码可登录并进入工作区 |
| 白名单放行 | 开启开关，确认 A 在白名单；用 A 获取验证码并登录 | 发码、登录成功，进入 A 的工作区 |
| 非白名单发码拒绝 | 开启开关，确认 B 不在白名单；输入 B 并点击“获取验证码” | 表单底部显示服务端 `msg`，例如“您暂无权限使用此产品，请联系平台管理员方正东”；按钮仍为“获取验证码”，不启动倒计时、不显示发送成功、不进入工作区 |
| 发码后资格被撤销 | 开启开关，A 在白名单时成功获取验证码；暂不提交，由服务端移除 A 并确认生效；在验证码有效期内输入刚收到的验证码并登录 | 显示服务端拒绝文案，恢复可提交的登录按钮，停留登录页；不进入工作区，不以笼统“登录失败”或离线页面替代该原因 |
| 恢复资格后重试 | 将 A 重新加入白名单并确认生效；保持当前客户端进程，在倒计时结束后重新获取验证码并登录 | 能重新发码、登录；客户端没有缓存上一次的拒绝结果。前一次成功发码产生的倒计时无需因登录拒绝而清零 |
| 密码登录兼容 | 开启开关，B 不在白名单；切换“密码登录”，输入有效密码、图形验证码并勾选协议 | 按当前服务端文档，密码登录仍可成功；客户端不因短信白名单拒绝而封锁密码登录 |
| dev 重启 | 完成一次成功登录，完整退出 Electron，再运行 `npm run dev` | 回到登录页，不自动恢复上一轮 dev 的登录；再次使用有资格账号可正常登录 |

发码被拒绝的用例还应由服务端确认没有实际发送短信。登录被拒绝的用例由服务端确认返回 `NOT_IN_WHITELIST`、`data: null`，未下发 token；涉及 C 时另核对没有新建账号。这些服务端副作用不能仅凭客户端页面判定。

本次不要求移出白名单后立即踢出已登录会话；文档尚未定义已有 token、刷新及会话恢复的白名单策略。验证登录阶段拦截时，应在提交登录前撤销资格。

## 4. 请求核对与定位

账号请求由 Electron Main 发起，登录页 DevTools 的 Network 面板不能作为完整抓包依据。需要核对线上请求时，使用测试网关日志或经团队配置的 HTTPS 抓包工具。

- 请求来源应为 `https://gapi-test.insight-aigc.com`。
- 发码仍使用 `POST /user-server/mobile/getSmsCode`，请求体为 `{ "scene": "LOGIN", "phoneNumber": "<测试手机号>" }`。
- 短信登录仍使用 `POST /user-server/loginV3`，请求体为 `{ "type": "PHONE_NUM", "info": { "phoneNo": "<测试手机号>", "code": "<验证码>" } }`。
- 发码、图形验证码、两种登录、刷新、用户详情和退出请求均应携带 `extInfo: {"client_type":"Desktop"}`；HTTP 头名称大小写不敏感，抓包显示 `extinfo` 也正确。
- HTTP 200 不等于业务成功：客户端按业务码处理 `NOT_IN_WHITELIST`，并展示后端 `msg`，不硬编码联系人。

对接文档中的登录路径写作 `/user/loginV3`，现有客户端经网关调用 `/user-server/loginV3`。本次保持现有路径；如测试环境返回路由错误，先与服务端核对网关映射，不凭路径差异猜测替换。若返回 `SUCCESS` 但预期应拦截，依次核对环境、请求头值、白名单开关及手机号资格。

验收记录保留客户端版本/提交、用例、时间、脱敏手机号、业务码和提示截图即可，避免记录验证码、密码、token 或 Cookie。

自动测试使用模拟服务端响应，覆盖全部账号接口的桌面请求头、HTTP 200 下的白名单业务拒绝、文案透传、拒绝时不保存 token/不发布已认证状态，以及资格恢复后的重试和密码登录委托。已有环境测试确认源码运行选择测试环境。

真实短信投递、测试网关映射、服务端白名单配置、数据库建号行为，以及表单显示和倒计时由上述手动用例验收。自动测试通过不代表这些服务端和界面行为已实测通过。
