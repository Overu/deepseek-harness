# 旧会话历史兼容修复

## 原因

旧 V3 日志保存了两条工具调用声明，但只记录一条 `tool/call`，没有记录任何 `tool/result`，随后以 `UNKNOWN` / `Cannot read properties of undefined (reading 'prepare')` 结束回合。故障发生在旧版本工具调度阶段。新 Core 的 V4 关系校验拒绝在 step 关闭时留下未结算调用，因此升级暴露了旧数据的不一致；保存的消息没有被删除。

会话打开失败后，模型选择投影无法获取，专家技能目录也无法读取。此前模型入口一直显示加载中，技能入口没有明确解释原因，形成了其他功能消失的表象。

## 修复行为

Core 的相邻 V3→V4 迁移只处理紧随同一回合 step/end 的上述确切错误，且要求存在未结算的已记录调用。已记录调用补入“执行结果未知”的错误响应；没有启动记录的声明补入官方 canonical `TOOL_NOT_STARTED` 响应。保留历史消息及原有结果，重映射后续本地引用，不执行工具、不虚构成功、不放宽原生 V4 校验。

桌面端模型入口显示加载失败状态；历史成功打开后恢复正常。专家技能入口解释因历史不可用而暂不可用。Harness 菜单提供只读导出：消息文本使用 Core 历史 codec 解码，原始 JSONL 导出保留物理记录，均不接入可写 Agent。输入及总解压内容限制为 32 MiB；保存拒绝覆盖会话代际文件及已有文件。

## 验证

- 五份本地 V3 历史副本全部迁移并重新打开；四份受影响历史各补入两条错误结果，正常历史没有额外补入结果。
- 使用桌面捆绑 Node 24.9.0 与编译后的 Core 持久化组件，五份副本均通过只读打开、V4 后继落盘、再次打开及历史文本导出；所有源文件哈希保持不变。
- 已安装 1.0.4 的原始 V4 读取器也接受全部五份新迁移产物；修复没有引入旧恢复基线无法读取的新格式。
- 安装包恢复验收加入脱敏的同类调度故障，由真实旧 V3 写入器生成，再通过 Candidate → 恢复 → Candidate 追加对话及重新打开。旧 Core 拒绝、新 Core 通过，正常和故障 V3 代际均校验原始文件未改动；三平台正式打包时执行同一验收。
- 压缩和未压缩日志、读写访问分别验证：只读不发布后继，写入发布经过校验的 V4 后继，新回合可以追加并再次读取。
- 保持普通结束、其他错误、缺少证据、回合不匹配和原生 V4 未结算调用的拒绝行为；迁移模块及新增辅助模块的针对性覆盖达到 100%。
- 用户主动卸载的第三方插件没有被恢复；账户数据及原始历史没有被修改。
- Core [三平台 Runtime 构建](https://github.com/Boxser567/insight-harness-core/actions/runs/37881665990) 全部成功。新标签为 `insight-runtime-v0.2.1-alpha.1-insight.3`，对应提交 `c3aaab2e76ddfad6163478687287774ad7233374`；Shell 已固定三平台资产来源和 SHA-256。

## 发布顺序

本次修复与已合并的本地插件导入、启动故障归因修复共同进入新版本。先提交及验证新 Core Runtime，再在新桌面版本固定三平台 Core 提交和校验值。既有 1.0.4、1.0.5 标签及资产保持不变，沿用 Candidate → 恢复验收 → Stable 的发布链路。

新桌面版本为 1.0.6。Core 的兼容性测试在生产依赖部署之前执行，避免 Runtime 打包裁剪开发依赖后无法启动测试；测试失败不会发布该平台 Runtime 资产。

当前发布门槛按用户最新要求调整：Core 三平台成功后先安排本地 1.0.6 Candidate 手动验收，用户明确确认通过后才触发 Shell 三平台 Candidate 构建及后续发布。
