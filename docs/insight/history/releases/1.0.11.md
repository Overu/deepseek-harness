# 1.0.11 Candidate 兼容发布记录

## 发布范围

用户明确授权用当前修复源码构建真正的 `1.0.11` 测试包，用于旧 Shell V2 迁入新客户端，以及新客户端后续 V3 更新路径验证。版本采用 final SemVer，但只发布三个目标的 Candidate V2，不发布 Stable，不覆盖已发布 rc.2 或旧 1.0.10 制品。macOS 使用正常签名、公证和最终验证；Windows 沿用已确认的当前用户无签名安装策略。

## 兼容路径和限制

旧 Shell 1.0.7/1.0.8/1.0.9 只接受 V2 final 清单，直接向它们投放 rc.2 不会生效。本次同功能修复源码重建为真实 1.0.11，不做版本别名或清单与安装包版本错配。当前新客户端同时读取 V2 和 V3，按已验签版本最高值选择；1.0.11 高于 1.0.11-rc.2，可由旧版 V2 reader 和新双协议 reader 共同发现。

安装 final 1.0.11 后，后续预发布应为 1.0.12-rc.1 或更高，不能把 1.0.11-rc.2 当作更高版本。常规检查仍只查 Stable，五连击手动内测检查才查 Candidate；版本本身为 rc 时才沿用已确认的 rc 常规发现策略。本地签名 fixture 可验证未来 V3 选择、防回放和版本比较，不会向生产发布未构建的 1.0.12-rc.1。

已安装的新 DSH 1.0.10、rc.1 的 Electron 空响应 URL 缺陷不能由服务端修复，仍需手动安装修复包一次。此限制与旧 Shell V2 协议兼容是不同问题。新包沿用原 Insight 应用身份和用户数据目录；元数据发现检查不替代真实原地安装及历史数据连续性验收。

## 验证和执行证据

打包前记录 Stable 及三个 Candidate V3 指针的签名字节摘要；发布只允许更改 Candidate V2，发布后按相同对象核对 Stable/V3 未变。旧 1.0.7 标签 reader、当前双协议 reader、真实 Electron/MacUpdater 的发现检查与后续 V3 本地 fixture 分开记录结果。实际覆盖安装、其他平台反馈仍按已有验收范围处理，不能因构建或清单通过改写为安装通过。

当前尚未记录构建和发布结果，完成后追加实际源码提交、run、目标和公开 CDN 验证结果。CDN 既有强缓存问题需复核，不能只凭 OSS 写入成功宣称公开发现已生效。

本轮新增的本地签名序列测试验证 V2 final 1.0.11 被接受后，更高 V3 1.0.12-rc.1 可被选择和记录；低版本 rc.2 回放被拒绝，持久版本下限保留。source/state/controller 三文件共 42 项测试通过；未来 rc 仅为本地 fixture，不是生产发布。

提交前打包 workflow／Candidate 发布器两文件 15 项测试通过，新增序列相关三文件 42 项通过，合计五文件 57 项；定向 lint 和空白检查通过。旧 Shell 三个 tag 的 V2 reader、公钥和分发配置一致，隔离 1.0.7 reader 已对当前 1.0.10 的 CDN 与原站三目标完成只读验签，作为路径预检；1.0.11 的真实发布验收仍需后续执行。
