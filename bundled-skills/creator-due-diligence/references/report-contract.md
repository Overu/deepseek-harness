# 报告与交接契约

报告呈现规范：1.5；结构化 JSON schema：1.2。完整任务默认保存 `report.md`、`evidence.md` 和 `due-diligence.json` 到本次任务输出目录；不写入技能目录。三个文件来自同一证据集。只回答局部问题时可缩减交付，未调查模块在结构化记录中注明。旧版报告不追溯补填；缺少新版字段代表未记录，不能解释成零样本。

## 结果报告与审计记录分层

最终对话答复是**决策摘要**：先给 `proceed / conditional / hold / exclude / insufficient` 对应的白话结论及适用合作身份，再给不超过三项改变决策的事实与证据，最后列签约前必须满足的条件或关键缺口。能用一段话说清就不铺章节；有完整报告时给链接，不在对话里重述全文。证据不充分时直说影响决策的缺口，不用一长串“未取得”冲淡结论。

`report.md` 是面向品牌决策者的**合作风险判断页**：先给合作结论，再列分维度判断，最后列签约前事项。每维1–2句，内容是“具体事实＋合作影响／处置建议”，必要日期、数字和来源就近附上。核心维度是账号与影响力、历史行为、竞品关系、本品言论、用户风评；转化方案、创意口号等泛营销内容另行处理。

正文的每句话都应回答“这个达人有什么事实或风险，对这次合作意味着什么，应该怎么办”。调查者的自我纠错、方法教学、通用免责声明、逐维采样限制不进入主报告；覆盖数量、未取媒体、排序／分页问题及证据充分性归入 JSON，原始证据放入证据册。用户询问研究范围时单独提供。

若尚缺的是现行合同、重大争议原文或明确身份，且它会阻止签约，写成具体事项，例如“由达人团队书面确认现有家电合作是否限制扫地机推广”；存在无法核实的重大指控时写“暂停签约，先核实该指控原文与回应”。这类事实缺口必须保留，不用“材料有限”替代具体问题。

短句示例：本品言论写“未发现针对本品的贬损或拉踩言论”，不接“未覆盖全部历史，因此不能写成从未拉踩”；账号项直接给账号和粉丝数，自我纠错放在与用户的更正说明中。争议意见明确写成“有用户质疑……”而不是事实定性，避免用额外免责声明修补不准确的主张。

`due-diligence.json` 保存结构化证据和客观审计记录，包括关键词、接口版本、查询状态、调用与费用、字段解析及实际覆盖。报告正文和最终答复不附这些执行记录，也不展示中间思考、自我检查、检索日志、工具调用或技能执行说明。用户明确询问方法、费用或审计明细时，另行提供对应客观记录，不混入业务报告。

`evidence.md` 是给业务人员核对的公开证据册：账号覆盖表（已确认/候选/未检出/不可取及实际采样量）、每项重要判断的代表材料与反例、争议的原始指控/回应/后续。每条用证据ID、日期、发布主体关系、必要短摘录、原文链接和核验状态呈现；优先2–5条有鉴别力的例证，材料不足则列实际数量。转载聚类合并展示，保留样本限定；不贴逐条评论全集、评论者身份或接口日志。

## Markdown 报告形态

1. **决策结论**：达人、品牌/产品、日期、`proceed / conditional / hold / exclude / insufficient` 的白话建议；一段话内说明最多三项改变决策的事实，以及决定性待核条件。区分“合同状态不明”和“已确认违约”，“样本未见负面”和“无风险”。
2. **分维度判断表**：优先用 `维度｜判断` 两列，每格给事实和合作影响，附代表来源。无实质发现的维度一句给出准确结果。证据充分性评级保存在 `evidence_adequacy`；主报告不用“样本有限”等标签填充每格。品牌提及仍按提及表述，用户观点仍按观点表述，重大争议保留指控、回应和状态。必要分母保留在支持具体统计判断的位置。
3. **签约前条件**：只列会改变推进决定的事项，通常 1–3 项，写清谁需确认什么。合同、排他和冷却期用直白语言表达，例如“确认现有合作是否限制本次竞品推广”；不把核验清单写成内部调查流水账，也不自动联系他人。
4. **资料入口**：末尾只链接证据册。采样平台、作品和评论数量、时间窗及技术限制集中保存在 JSON；用户要求时单独输出研究范围，不把该部分作为主报告固定章节。

### 主报告写作骨架

标题为“达人 × 品牌／产品｜合作背调”，附核查日期，正文采用以下三个部分：

- **合作结论：** 开头直接给“建议合作／建议先做短期合作／暂缓合作／不建议合作”，随后说明最重要的1–3项理由。若无法给出建议，点名尚未确认的具体身份或重大事件及下一步；不用“进入评估”等过程状态代替决定。
- **分维度判断：** 用“维度｜判断与合作影响”表格。每格先说结论，再用必要事实说明风险及影响；无实质发现的维度一句结束。账号与粉丝、历史行为、竞品关系、本品言论、历史内容与用户反馈按合作相关性组织。
- **签约前事项：** 只保留决定签约或上线的事项，写成“由谁＋确认什么／执行什么＋何时完成”。没有实际待办就不凑项，末尾链接证据册。

交付前逐句检查：保留达人事实、具体风险、合作影响和必要动作；删去调查者的自述、方法教学、重复的取样声明和无关营销策划。行业术语改成日常表达，校对姓名、品牌、日期、数字和链接。争议意见标明发言主体，未知合同状态写成具体确认事项；精简呈现不改变事实及其核验状态。

## JSON 顶层对象

1.2 新报告必有字段：`schema_version`（"1.2"）、`report_id`、`generated_at`（含时区）、`scope`、`accounts`、`account_inventory`、`sampling_plan`、`coverage`、`queries`、`evidence`、`evidence_adequacy`、`events`、`brand_relationships`、`brand_statements`、`content_samples`、`term_clusters`、`sentiment_samples`、`decision`、`cost`、`due_diligence_handoff`。读取1.0/1.1时不假定新增数组已有采样结果。

空列表只表示没有可记录条目；某模块是未评估、未检出还是获取失败，由 `coverage.modules` 明确解释。数值未知为 null，不使用 0 代替。

### scope 与 accounts

- `scope`：品牌/产品、竞品列表、拟合作时间、目标平台、目标历史时间窗、适用品牌规则（每条有 `rule_id`）、预算授权引用。
- `accounts[]`：`creator_key`、平台、稳定 ID、昵称、主页、`entity_cluster_id`（可空）、身份状态及证据 ID、粉丝数/来源/抓取时点（可空）。所有平台 ID 使用字符串。
- `account_inventory[]`：每个范围内平台一条，含 `platform`、`search_status`（checked/partial/unavailable/not_run）、检索词与查询ID、`candidates[]`（账号ID/主页、confirmed/candidate/excluded、归属类型、身份依据ID、公开活跃时间、是否采样与原因）、发现缺口。完整国内背调的八个平台均有记录；缩减范围说明用户依据。
- `sampling_plan[]`：按账号或第三方来源层记录 `plan_id`、平台、账号ID、窗口、优先级、作品/评论目标、分层与排序、实际取得/去重/相关量、完成状态、`stop_reason`、差额原因和查询ID。预算调整目标保留原目标与调整原因，不把目标改小后伪装原计划全部完成。

### coverage 与 queries

- `coverage.modules`：公开争议、竞品关系、本品言论、历史作品与话题、作品评论与用户反馈五模块各自 `assessed / partial / not_assessed / unavailable`，以及原因。历史作品与评论可分别为不同状态。
- `coverage.platforms[]`：目标平台、实际最早/最晚内容日期、发现的作品总量（未知为 null）、已取作品数、内容审阅数、已取评论数、各来源层与排序、缺口及对决策的影响。无法得知总体总数时不编造覆盖百分比。
- `queries[]`：`query_id`、平台、关键词/过滤器、端点/方法/版本、文档核查时间、运行时间、页数、原始条数/去重条数、结果状态、停止原因、来源缓存时间、估算/实际费用、脱敏请求标识。
- 结果状态区分 `success / empty / failed / not_run`；接口文档状态与此次运行状态分开。

### evidence：共享证据索引

每条包含：

`evidence_id, platform, creator_key, content_id, source_url, source_type, origin_cluster_id, published_at, event_at, captured_at, quote, context, media_timestamp, extraction_method, review_scope, identity_status, raw_artifact_ref, supports_claim, contradicts_claim, limitations`。

- 缺失时间/原文链接可为 null，但需说明无法独立回溯的影响，不能作为已独立核验的唯一证据。
- `source_url` 使用无令牌公开永久链接；受控授权资料用本地脱敏引用，不公开合同或个人资料。
- `quote` 仅保留支持判断所需短摘录；完整内容留在获准的受控存储中。评论者不输出多余 ID、个人主页或私人信息。
- `review_scope`：`title_only / excerpt / full_text / full_media_review`；不能把模型概括当原话。
- API 文档是能力证据，不是达人行为证据；两者不要混列成同一事件支持材料。
- 新证据增加 `publisher_key`、`publisher_relation`（self/partner/third_party/authority/unknown）、`text_cluster_id`（可空）和 `account_identity_status`。`origin_cluster_id` 聚合同一原始材料；一稿多发与多人转述分开记录，不能由篇数自动推断独立性。

### evidence_adequacy：每项判断的支持程度

逐项记录 `claim_id`、`claim`、`evidence_ids`、`status`（supported/limited/insufficient/not_assessed）、实际平台数、不同作品数、相关去重评论数、`origin_cluster_count`、`publisher_count`、`independent_source_count`（未知为null）、时间窗、反证/回应状态、限制与下一步。计数由真实关联材料去重得到，不能把全任务样本量复制给每项判断。`supported` 表示足以支持该限定主张，不等于统计代表性或结论无风险。

### 发现与样本

- `events[]`：事件 ID、标题、具体主张、对象账号、发生时间、状态、来源聚类、支持/反驳证据 ID、回应查找状态、严重性及依据、传播范围、品牌相关性、人工核验状态、下一步。
- `brand_relationships[]`：关系 ID、账号、品牌/产品、关系类型、证据 ID、发布时间、有效期、排他状态及证据、置信度、待核事项。字段枚举见调查规则。
- `brand_statements[]`：言论 ID、账号、目标品牌/型号、说话者、立场、表达性质、原话证据 ID、上下文覆盖、商业背景证据、判断、人工核验状态。恶意动机未知就保持未知。
- `content_samples[]`：样本 ID、账号/平台、抽样框与规则、目标和实际时间窗、发现作品数（未知为 null）、入样作品 ID/证据 ID、普通/商业/未知类型数量、仅元数据/正文/完整媒体审阅数量、表现字段口径、偏差及缺口。篇数为零时说明是未取、查询为空还是确无可见作品。
- `term_clusters[]`：词项 ID、`native_hashtag / creator_term / audience_term` 来源层、原词与归并词、提取/归并方法、时间窗、匹配的不同作品数或评论数、各自分母、证据 ID、异常/歧义说明。不能把样本内高频直接标成平台热榜。
- `sentiment_samples[]`：样本 ID、平台、作品层、评论来源层、入样作品 ID/数量、选帖及选评论规则、时间窗、排序/分页、采集数/去重数/对象相关数、positive/neutral/negative/uncertain 计数、分母、公式、值（或 null）、主题及其命中计数/涉及作品数、代表证据、局限。精选评论标注 `featured_only=true`，不得混入代表性样本。无法获取评论时数组为空且 `coverage.modules` 说明，不用 0% 表示。

### decision 与 cost

`decision`：`action`、理由、证据 ID、关键缺口、前置条件、人工复核状态、有效范围。

`cost`：币种 USD、授权上限、此前支出、此次实际额（未知为 null）、此次保守估算、剩余预留、计费依据、停止原因。若只使用资料或文档，API 调用次数 0、本次 API 费用 0；不能据此说全部研究成本为零。

### due_diligence_handoff

供 `creator-recommendation` 或其他上游消费，不依赖其存在：

```json
{
  "handoff_id": "ddh-example",
  "report_id": "dd-example",
  "creator_keys": ["xiaohongshu:example-id"],
  "entity_cluster_id": null,
  "decision": "hold",
  "risk_findings": [],
  "hard_conflicts": [],
  "unresolved_checks": [
    {"check_id": "check-1", "question": "争议原文与后续是否取得？", "required_evidence": "原始内容及后续回应", "blocks": "正式签约"}
  ],
  "evidence_ids": [],
  "coverage_limits": ["示例对象，未执行真实查询"],
  "recheck_before": null,
  "report_ref": "report.md"
}
```

这是结构示例，不是有效报告。实际交接应带真实账号与证据；严重指控未复核或覆盖不足时不得凭空填充。

`hard_conflicts[]` 每项必须有 `rule_id`、已核实事实、证据 ID、有效时间和复核状态。未知排他期不能放入硬冲突。上游保留原商业评分，单列背调门槛；是否改推荐结论由上游按证据决定，不覆盖历史版本。

## 一致性验收

- 每个证据 ID 唯一；发现和结论引用的 ID 均存在。转载来源聚类不重复计算独立证据。
- 标为 verified 的对象与原文匹配；“收到指控”与“指控成立”分别核验。
- `exclude` 有适用规则与核实事实；人审未完成不伪造完成。身份不明的负面内容不能归到目标账号。
- 情绪计数与分母相符；明确被排除样本；0 分母不产生比例。选择性样本不产生全网情绪结论。
- 作品/评论/热词各有独立分母和时间窗；原生标签、作者表达、受众表达不混算。若报告称“系统分析用户反馈”，必须存在可追溯的评论抽样记录；只有媒体报道或标题时须降级为未完成。
- 平台盘点与深采样完成度分别核验；所有已确认本人账号有采样结果或停止原因。每个重要判断对应支持程度记录，第三方讨论与品牌/本人账号分别标注，转载不重复算原始来源。
- 目标时间窗与实际最早内容时间分开；内容发布时间不能被抓取时间覆盖。
- 缺少模块或接口失败的状态与原因保存在 JSON；缺失项阻止签约时，摘要写出具体阻止事项及所需确认动作。报告不包含认证头、密钥或临时签名链接。
- 当前包无自动 JSON 校验器：由执行代理逐项核验，不能把“字段都填了”当作证据真实或判断正确。
