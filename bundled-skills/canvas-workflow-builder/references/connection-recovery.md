# 连接异常、未知结果与断点恢复

收到 `CLIENT_UNAVAILABLE`、`CONTEXT_NOT_READY`、连接/读取超时、未知或相互矛盾的回执时读本篇。恢复动作沿用用户原任务与运行授权，不能扩大生成数量、切模型、重建画布或代替用户刷新/重启客户端。

## 1. 先分清已知事实

| 实际证据 | 可得结论 | 下一步 |
|---|---|---|
| `CLIENT_UNAVAILABLE` | 当前请求没有找到可用 Client，或其连接已失效；具体原因看原 message | 保存回执，进入有界只读检查 |
| `CONTEXT_NOT_READY` / `READ_TIMEOUT` | 上下文/能力尚未确认，或等待超时；不等于提交确定失败 | 先区分只读、明确未生效、未知/部分成功 |
| `canvas_get(view:"summary")` 成功 | Host 能读取该画布摘要 | 不据此宣称 Client 就绪、写入可用或取得 confirmed 版本 |
| 故障后 `nodes` / `graph` 返回 `read` / `graph` | Client 读取路径在该时刻成功 | 检查 consistency、截断/缺失与目标状态；编辑/运行能力另看回执 |
| `rejected` + `effect:"none"`，且无未知码/部分成功 | 这一操作明确未生效 | 就绪、版本/授权/现状核对后，才可继续这一个操作 |
| `partial` / `completed[]` / `paused` | 某个前缀已保存或受理 | 保留成功项及任务身份；`nextIndex` 仅定位，不授权整批重发 |
| 任一未知状态/错误码，或 `rejected/effect:none` 与未知码并存 | 结果仍不确定 | 进入第 3 节，不用失败重试路径 |
| `AUTH_REQUIRED` / `EDITOR_BUSY` / `CLIENT_AMBIGUOUS` | 需处理登录、用户编辑或 Client 归属 | 保存断点并说明真实阻塞，不反复探测或绕过 |

alpha.31 的原生 Store 在前端常驻服务运行，通过 HTTP/SSE 桥连接 Host。关闭画布视图不等于关闭 Client；一直停在同一会话也不保证桥始终可用。没有连接日志时，不能断言是网络抖动、用户切页、版本太旧或必须打开侧栏。

## 2. 有界只读检查

1. **记录同一故障的起点与断点。** 保存 canvasId、操作类型、目标节点、失败时间、错误 code/message/retry、requestId、已完成项及 taskId/jobId。失败回执重复出现的 version 可能是原输入，不能当成故障后的 confirmed 读取。
2. **默认预算：累计 60 秒、最多 3 次只读探测，以先到者为准。** 包含此前已经耗去的等待/调用时间；换节点、换工具、换画布或另开一轮推理不重置。用户给更短期限或要求暂停时服从。工具调用本身若超过预算，返回后立即收尾，不追加新调用；不承诺 skill 能中止插件内部 pending 请求。
3. **探测原画布。** 有真实已知节点 ID 时用 `canvas_get(canvasId, view:"nodes", nodeIds:[该ID], refresh:false)`；没有已知节点时省略 `nodeIds` 读取原画布的 nodes。nodes 不传 `limit`，不编造健康检查工具，不换新画布试连接。`summary` 可辅助看摘要，但不算 Client 恢复证据。
4. 首次可立即探测；仍失败时，剩余预算允许才分别等待约 10 秒、20 秒后再探测。使用现有等待能力；返回后台等待 Job 时先确认等待已结束。不要密集轮询，也不要让每次模型/工具往返另起一轮预算。
5. **读通后核对再续跑。** 需要写入时，读取相关节点的当前内容及 confirmed 版本；`unconfirmed` 才考虑显式 `refresh:true` 权威重读，它会重载可见画布。遇到用户正在编辑/未保存内容时先处理该阻塞，不强制重载。核对用户新改动、依赖产物、原授权和成功前缀；不能机械地换 expectedVersion 覆盖。
6. 只对原回执明确未生效、当前仍需执行且符合授权的剩余操作，**最多自动恢复重试 1 次**。必要时缩为已核实的未执行项，保留原目标/参数，版本使用核对后的 confirmed 值。只读成功不重置预算；该次业务操作仍报连接问题，就停止自动恢复。读通不保证 edit/run 能力，不用额外业务写入“验证一下”。

不以 `canvas_create`、`canvas_node_edit`、`canvas_run`、`canvas_process`、素材导入或 `canvas_open` 探活；它们会产生业务动作，且 `canvas_open` 本身也依赖桥。有限探测是恢复策略，不代表“前几次一定正常”。

## 3. 未知结果保持原请求身份

- `submission_unknown`、`upload_unknown`、`create_unknown`、`monitoring_unknown`，以及 `SUBMISSION_UNKNOWN` / `ASSET_UPLOAD_UNKNOWN`，都不等于已成功或已失败。`retry:never_auto` 不得被“赶时间”“以前第六次就好了”覆盖。
- **有 jobId：** 用原 `job_output` 查询；受理中、监控未知或等待超时均不重新提交。已有 taskId/operationId/requestId 也保留，使用当前工具实际支持的查询；没有查询能力就说明缺口，不能臆造接口或直接访问私有桥/凭据。
- **没有 jobId，或字段矛盾：** 读取相关节点、原任务状态、版本及受理记录，按身份关联。`job_list` 没新任务、outputs 仍旧、没有 results 或没有 jobId 只能说明本地未确认，不能排除后台已受理；confirmed 版本也不能证明某次 run 没提交。
- **恢复写入：** 权威读回若已存在预期修改，标记完成而不重做；未读到修改不能单独排除旧请求仍在途。仅当原请求的权威记录明确未派发/未受理，且无在途或未知项、授权仍有效时，才把“重提一次”列为可执行后续。缺此证据就保持待核验，不把重复风险伪装成普通重试。
- **批量：** `completed[]` 的成功前缀不重放；检查 `failure` 内的未知码及每项真实回执。未知项先核验，`nextIndex` 不能跳过核验；剩余项按最新现状与授权重新形成最小操作集合。
- 只有“先搭建”的授权时，恢复后继续配置与连线并交付待运行清单；用户说“继续”不自动变成生成授权。已有运行授权也不自动扩展到重跑、增加数量或修改模型/规格。

## 4. 停止自动恢复并交接

预算耗尽、一次恢复业务重试仍失败、结果未知且无法权威核验，或用户要求暂停时，停止自动探测与业务重发，保存断点。不为维持进度而打开别的画布、刷新窗口、重启 Harness、改插件、读取连接配置/凭据或调用未公开接口。

对用户说明当前完成项、仍受阻的一项、最近可验证事实和已保存断点。示例：

> 节点和连线已保存，最后一项配置尚未生效；当前会话的画布 Client 仍不可用。我已停止自动重试并保存断点，连接恢复后可先核对状态再继续。

未知提交应改为“这次提交结果尚未确认，正在按原任务核验”，不能说“没扣费”“肯定没提交”。故障前读取成功不等于故障后读取正常；只有 summary 成功时就明确说“摘要可读，Client 路径未确认”。

需要协助时，准确说明缺少哪项诊断信息，例如故障当时 events/client-event 的状态/耗时、session 绑定与 stream 状态；不要求用户先刷新来证明问题，不把重启/切页说成必需操作。用户报告恢复或明确要求重试后，先做只读核验再续未完成项；单纯时间过去不算恢复，用户的新要求也不消除未知提交的重复风险。
