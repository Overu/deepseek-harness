# 文本节点提示词工程

这份文档解决两件事：**文本节点（LLM 节点）的指令怎么写**，以及**根本不用 LLM 节点时怎么把成品文本放进画布**。用户点名要求「文本节点怎么写提示词、怎么选模型」，答案都在这里。参数枚举与运行纪律见 `references/models-and-params.md`。

> 实测口径：81 条模板共 65 个 text 节点 = **31 个 LLM 生成节点**（`params.prompt` 非空）+ **34 个文本输入节点**（`value` 存用户填的素材）。LLM 指令长度：中位 **410 字**，均值 630 字，范围 7–4398 字。

---

## 1. 先划清能力边界（决定后面所有写法）

| 动作 | agent 能不能做 | 工具与字段 | 失败形态（实测） |
|---|---|---|---|
| 写 LLM 指令 | ✅ | `canvas_node_edit(ops:[{op:"add"\|"edit", …}])`，`changes.prompt` → 落 `params.prompt` | — |
| 写文本正文 | ✅ | `changes.text` → 落 `data.value`（≤32768 字） | — |
| 给文本节点选模型 | ❌ | `changes.params.model` → `INVALID_ARGUMENT`；`configure` → `UNSUPPORTED_NODE` | 只能用户在画布 UI 选 |
| 运行文本节点 | ❌ | `canvas_run` → `UNSUPPORTED_NODE`（公开生成只支持普通 image/video/TTS audio） | 必须用户在画布点生成 |
| 读回结果 | ✅ | `canvas_get(view:"nodes")` 从 `data.value` 读 | 结果落 `data.value`，不是 `params.prompt` |

两个直接推论：

1. **凡是「要 LLM 现跑」的设计，都要在计划的 `manualSteps` 里登记一条**，并写清用户要点什么（选模型 + 点生成）。没登记的 T1 节点 = 计划不完整。
2. **模型选型只能作为交付物交给用户**：技能不能替用户选，但必须给出「这个任务建议用哪个」的结论和理由（§8）。

> 来源口径：错误码枚举（`UNSUPPORTED_NODE` / `INVALID_ARGUMENT`）与 `canvas_node_edit` / `canvas_run` 的字段约束来自插件源码；上表第三列的**回执文案**属实测观察，插件 bundle 内不含这些中文串（由客户端原生层返回），引用时以错误码为准。

另外记住：图上、视频上连来的文本只有**运行后**才有内容。文本节点没跑，下游节点拿到的就是空——这决定了 §2 的 T1/T2 取舍。

## 2. 双模式：T1 LLM 节点 vs T2 代笔节点

| | **T1 LLM 节点** | **T2 代笔节点** |
|---|---|---|
| 定义 | agent 只写指令（`changes.prompt`），正文留空，用户点生成后 `value` 由模型产出 | agent 直接把成品文本写进正文（`changes.text`） |
| 谁来产出内容 | 画布里的 LLM（模型在 UI 选） | agent 自己（在本轮对话里写好） |
| 全链可自动跑通 | ❌ 必须用户点一次生成 | ✅ 只要下游依赖就绪即可 `canvas_run` |
| 结果可复现 | 每次点都会变（发散） | 逐字确定，可回读、可校对 |
| 依赖 | 依赖上游图/文已就绪，且用户会去点 | 只依赖 agent 写对 |
| 计划字段 | `textMode:"llm"` + `prompt` + `manualSteps[]` | `textMode:"copy"` + `text` |
| 失败成本 | 用户点一次不满意要再点 | 写错了 agent 改一次即可 |

### 选择判据（按顺序问自己）

1. **「这批文本要一次定稿，还是每次生成都该不一样？」**
   - 一次定稿、要可控可校对 → **T2**
   - 每次点都该有新鲜发散（灵感、多版本文案、风格探索）→ **T1**
2. **「下游必须自动跑完吗？」**
   - 用户说的是「帮我做出这 4 张图」→ 中间夹一个必须人工点击的 T1 会打断全链 → 优先 **T2**（agent 在本轮把 4 条描述直接写好）
   - 用户要的是「给我一个能反复用的模板/工作流」→ **T1** 更合适
3. **「内容需要引用画布上还没有的实时信息吗？」**
   - 需要模型看图再写（如「分析这三张包装图的风格，用 3 个词概括」）→ 这种判断 agent 也能做，但**若必须由画布侧模型看原图**，就只能 **T1**
   - agent 本轮就能拿到并判断的信息 → **T2**
4. **「文本节点是不是本来就该在画布上被用户改？」**
   - 用户会反复改这段文本再重跑 → **T1**（`params.prompt` 和 `value` 都是画布上可改的）
   - 只是给下游喂参数 → **T2**

### 三种典型需求的判定结论

| 需求 | 判定 | 理由 |
|---|---|---|
| 「裂变套图：一张产品图出 4 张不同景别」 | **T1**（照抄模板 A3 做法） | 4 条画面描述需要模型看图后发散；用户接受点一次生成 |
| 「做 3 张 3:4 主图，一张海报、一张细节、一张场景」 | **T2** | 三条描述 agent 本轮就能写死；全链可自动跑通，用户只要等结果 |
| 「给我一套能反复用的口红带货工作流」 | **T1** + `manualSteps` | 用户要的是可复用骨架，愿意自己点生成换口味 |

### 混用时的四个坑

1. **同一个文本节点不要又当 T1 又当 T2。**`value` 是 LLM 的输出落点：写了 `changes.text` 之后用户一点生成，内容就被覆盖。要么留空让模型写，要么写死不让它跑。
2. **T1 节点必须有 `manualSteps`，并且要提醒用户「先运行文本节点、再运行下游图像/视频节点」**。顺序反了，下游拿到空输入，生成的图就没有「结合【套图N描述】」的效果，人还以为技能坏了。
3. **T1 + T2 混在一张画布时，两类节点的标题要能一眼区分**（如 `灵感生成（需你点生成）` vs `画面描述（已写死）`），否则用户分不清哪个要点。
4. **锚点命名必须上下游一致**（§4）。T1 产出 `【套图1描述】`，下游就必须写 `【套图1描述】`；T2 也一样，写死正文时锚点是自己定的，更要前后对齐。

## 3. LLM 指令的六段骨架

模板实测：31 条 LLM 指令里，`不要输出任何…` 13 次、`精简中文` 8 次、`输出格式` 10 次、`任务目标` 5 次、`核心约束` 4 次、`# Role` 4 次、`角色描述/角色设定` 各 3 次。**最短可用骨架只要三段：任务目标 + 核心约束 + 输出格式。** 追求稳定时补齐六段。

| 段 | 作用 | 必须 | 常见标题写法（实测） |
|---|---|---|---|
| `# Role` / `## 角色描述` | 给模型一个专业身份与能力边界 | 建议 | `# Role: 资深美妆商业广告美术指导`、`角色描述`、`角色设定：` |
| `## 任务目标` | 一句话说清产出什么、给谁用 | ✅ | `## 【任务目标】`、`# Goal:`、`任务` |
| `## 输入说明` | 说明上游连入了哪些图/文，以及怎么指代 | ✅（有输入时） | 无固定标题，写在任务目标里 |
| `## 核心约束` | 一致性、禁止项、视角/动作红线 | ✅ | `## 【核心约束】`、`# Constraints (绝对准则):` |
| `## 差异化维度` | N 路输出之间**怎么变**（N>1 时必写） | N>1 必须 | `## 【差异化生成维度】`、`Workflow (三个维度的场景构建)` |
| `## 输出格式约束` | 分几段、每段什么标记、每段写什么 | ✅ | `## 【输出格式】`、`# Output Format`、`**输出：**` |

### 3.1 `# Role`：给身份 + 给能力清单

模板原文（`tpl_23` 的角色段，截断）：

> 你现在是一个专业的 AI 视觉提示词生成器，擅长为 AI 绘图模型生成高质量、真实精致、具有电商视觉冲击力的"化妆品包装组合展示图"提示词。你深度理解美妆品牌包装设计、视觉陈列、材质表现、组合摆放方式与商业拍摄逻辑，并能够构建"构图系统 × 视角系统"的统一视觉方案。

`tpl_15` 只写一行 `# Role: 资深美妆商业广告美术指导`；`tpl_61` 用 `**角色：**时尚艺术总监（Vogue风格、Harper's Bazaar风格）。` 起头。
**要点**：身份里带上「你熟悉 X、Y」比只写头衔有效；输出要给某个具体模型用时直接点名（`编写Nano Banana Pro提示词`、`适配 即梦、通义万相`）——模板确实这么做。

### 3.2 `## 任务目标`：一句话，含产出物与数量

模板原文（`tpl_10` / `tpl_32`）：

> **【任务目标】** 基于提供的参考图1，构思并描述4张该产品的系列展示图。
> `# Goal:` 根据用户输入的色调和风格和图1产品，结合珠宝产品特性，输出3组不同场景的中文AI绘画提示词。

**要点**：把「几张/几组/几段」写进目标句。数量写在目标里，和 §4 的输出格式段呼应，模型分段才不容易少给或多给。

### 3.3 `## 输入说明`：点名上游连了什么图，并规定指代方式

最容易漏、也最影响成败的一段。两种写法（均可）：

> 基于提供的参考图1，构思并描述4张"汽车+模特"的系列展示套图。（`tpl_68`）
> **核心约束：** 必须保持与参考图一致的场景氛围、光影色调、人物特征/产品外观，无需在描述中重复这些固定背景信息，参考图中主体，如无模特则不要做新增模特的描述（`tpl_10`）

**要点**：① 明确「参考图1 / 参考图2」各是什么，模型才不会把两张图混着描述；② 明确**指代方式**——`无需描述模特服饰和产品等已知信息，直接用"模特"和"产品"描述`（`tpl_61`），能显著压缩输出、避免复述输入；③ 明确**信息缺口怎么处理**——`如无对应文案信息则直接省略，不做虚构、不强行补充`（`tpl_14` 的字段约定，可移植进指令）。

### 3.4 `## 核心约束`：一致性 + 禁止项 + 兜底，三类都要有

模板原文（`tpl_15` / `tpl_32`，两段合并看）：

> `## 【核心约束】`（`tpl_15`）**一致性原则**：严格继承参考图的**场景氛围、光影色调、模特特征及产品外观**。不要在输出中重复描述这些背景信息。**主体原则**：若参考图无模特，输出内容严禁凭空增加模特，仅对产品进行静物构图变换。**视角限定**：严禁使用90度垂直拍摄。
> `# Constraints (绝对准则):`（`tpl_32`）**风格一致性**：所有输出必须严格服从{色调}和{风格}，严禁使用与该风格冲突的预设材质，**如无填写则根据产品输出合适且统一的色调和风格**。三个场景为统一色调和风格。**视觉减法**：严禁文字、水印、复杂背景。

**要点**：`tpl_32` 那句「如无填写则…」就是**兜底**——没有兜底，模型容易因缺参数而空转，或输出「未提供色调」这类废话。

### 3.5 `## 差异化维度`：只在 N>1 时写，且每个维度给可选值

模板原文：

> **【差异化生成维度】**（`tpl_10`）请在以下维度进行运镜与动作的创意发散，确保4张图在视觉上既统一又有明显区别：1. **景别切换：** 在特写（强调质感）、中景（强调交互）、全景（强调氛围）之间切换。2. **交互细节：** 改变模特与产品的互动方式或产品摆放方式（如无模特则改变产品摆放方式或展示细节）3. **视线与情绪：** 调整模特的视线方向（看镜头、看产品、看远方）及微表情。
> （`tpl_68` 汽车主题版）1. **景别与车辆视角：** 在全景…中景…特写…之间切换。2. **人车交互动作：** 单手搭在方向盘上、斜靠在引擎盖、拉开车门回眸、坐在车尾箱边缘、透过车窗看向外侧等。3. **视线与姿态情绪：** 飒爽、慵懒、随性、高级感。
> （`tpl_23` 双变量版）👉 **构图不同 + 视角不同，但场景完全一致**；**必须保持完全一致**：场景环境 / 产品组合关系 / 光线方向与光影结构 / 色调与氛围 / 材质表现；**视角变化（必须）**：从俯视、正视、45度、低角度仰视/Hero Shot、侧视、特写/微距、长焦压缩、前景遮挡构图中选 4 个（**不可重复**）。

**要点**：给**可选值清单**模型才能直接组合；只写「要有区别」输出往往趋同。`tpl_15` 把 `tpl_10` 的第 3 条改名 `视线引导` 是同一套维度的收敛写法，可直接沿用。

## 4. 输出格式契约 + 锚点切片（A3 原型的核心技巧）

### 4.1 机制

LLM 一次推理产出 N 段带方括号标记的文本；N 个下游图像/视频节点各连一条 `text_source→*_target` 边，在**自己的提示词里点名要哪一段**。切片不靠接口，靠**文本锚点**：

```
文本节点.params.prompt   →  “【套图1描述】…【套图4描述】” 的输出格式契约
文本节点.data.value      →  实际产出 4 段带锚点正文
        │ text_source
        ├──────────────→ 图节点1.prompt: 结合【套图1描述】描述 prompt，生成新的画面
        ├──────────────→ 图节点2.prompt: 结合【套图2描述】描述 prompt，生成新的画面
        └──────────────→ …
```

证据：`tpl_10` / `tpl_60`（指令 580 字 + 产出 341 字）、`tpl_15`（指令 756 字 + 产出 392 字）、`tpl_68`（指令 758 字 + 产出 428 字）四条模板都是这个结构；`tpl_20` 用 `【灵感1描述】…【灵感4描述】`、`tpl_23` 用 `灵感 1 / 灵感 2 / 灵感 3 / 灵感 4`、`tpl_61` 用 `[模特姿势]+[互动]+…` 的加号槽位式。**锚点名里出现的数字是「第几路」，不是「第几张参考图」**，不要混。

### 4.2 官方式锚点契约（直接复用）

**LLM 指令尾部（写入 `changes.prompt`）：**

```
## 【输出格式约束】
请严格按照以下格式输出，精简中文，不要输出任何引言或解释：

【套图1描述】
(此处填写：景别 + 模特具体动作与产品交互/产品展示 + 视觉焦点)

【套图2描述】
(此处填写：景别 + 模特具体动作与产品交互/产品展示 + 视觉焦点)

【套图3描述】
(此处填写：景别 + 模特具体动作与产品交互/产品展示 + 视觉焦点)

【套图4描述】
(此处填写：景别 + 模特具体动作与产品交互/产品展示 + 视觉焦点)
```

**下游图像节点提示词（写入各自的 `changes.prompt`，四处只有锚点号不同）：**

```
基于图1参考（保持模特和产品特征、产品文字细节及大小比例不变），结合【套图1描述】描述 prompt，生成新的画面
```

这两段一字不改就是 `tpl_10` / `tpl_60` 的原文（57 字 + 锚点段），实测产出见 `tpl_10.value`：4 段描述，每段 60–70 字，首句就是景别（`面部与肩颈特写…`／`半身侧面中景…`）。**这是整套模板库里性价比最高的一段可复用结构。**

变体清单：

| 变体 | 指令侧写法 | 下游侧写法 | 证据 |
|---|---|---|---|
| 4 段套图 | `【套图1描述】…【套图4描述】` | `结合【套图N描述】描述 prompt，生成新的画面` | `tpl_10` `tpl_60` `tpl_68` |
| 4 宫格一次出图 | 同上 | `结合描述 prompt生成新的4宫格画面` + `左上为【套图1描述】画面` … `右下为【套图4描述】画面` | `tpl_15` `tpl_68` |
| 灵感式 | `【灵感1描述】…【灵感4描述】` | `提取灵感N的画面描述，生成…` | `tpl_20`（下游还追加了 `禁止出现模特脸部`） |
| 灵感式（无方括号） | `以"灵感 1""灵感 2"…开头` | `提取灵感 N的灵感，生成…` | `tpl_23`（每段用双引号括起） |
| 加号槽位式 | 输出格式模板：`` `[模特姿势]+[互动]+[镜头与构图]+[背景]+[光照/色调]+[风格]` `` | 不需要切片（每节点独立跑一次 LLM） | `tpl_61` |
| 单段直出 | `请直接输出一段完整的中文提示词` | 下游整段接收 | `tpl_33` |

### 4.3 成对模板：LLM 指令 + 下游图像节点提示词（可整段复用）

**场景：1 张产品图 → 4 张不同景别的商品套图（agent 侧 T2 版本，文本写死）**

文本节点 `changes.text`（把 §4.2 的产出格式直接填成内容，锚点保持一致）：

```
【套图1描述】微距特写，产品正面 45° 立于哑光石台上，背景纯净渐变，侧逆光勾出边缘高光，视觉焦点在瓶身磨砂质感与 Logo 清晰度。
【套图2描述】中景，产品与配套包装盒的高低错落组合，顶光柔化阴影，视觉焦点在组合关系与包装烫金细节。
【套图3描述】全景俯拍，产品置于极简几何道具构成的浅色场景中，大面积留白，视觉焦点在整体陈列氛围。
【套图4描述】手持特写，画面不出现人脸，仅展现手部握持产品的姿态，柔光包裹，视觉焦点在手部线条与产品比例。
```

图节点 1–4 的 `changes.prompt`：

```
基于图1参考（保持产品外观、材质、文字细节及大小比例不变），结合【套图1描述】描述 prompt，生成新的画面
```

（图节点 2/3/4 依次替换 `【套图1描述】` → `【套图2描述】`/`【套图3描述】`/`【套图4描述】`。）

这套结构下：**只有图节点进 `runs`**，文本节点既不在 `runs` 里、也不需要 `manualSteps`（T2），全链可自动跑通。

### 4.4 锚点契约的四条硬规则

1. **锚点名上下游必须逐字一致**：多一个字、少一个方括号都不行（`【套图1描述】` ≠ `【套图一描述】` ≠ `套图1描述`）。
2. **锚点数 = 下游节点数**：LLM 要出 4 段就写 4 个锚点；下游有 5 个节点要 5 段，指令里就必须出现 5 个锚点。段数不匹配时，多的那路会没内容可用。
3. **锚点段要有「填写说明」**：官方模板里每个锚点下都跟一句 `(此处填写：景别 + … + 视觉焦点)`。这是让 4 段各自成型、互不雷同的关键——只给锚点不给说明，输出容易四段同质。
4. **必须禁止模型加解释和前后缀**：`不要输出任何引言或解释`（见 §5）。否则 `value` 里会带上「好的，以下是为您构思的 4 张套图描述：」这类污染，下游引用时更难对上。

> 更稳的做法（实测有效）：**下游节点不要只依赖上游文本，自己也要能独立跑通**。见 `references/prompt-craft.md` 的「自包含原则」。

## 5. 护栏句式清单

模板实测分布：`不要输出任何…` 13/31 个 LLM 节点、`不要` 16/31、`精简中文` 8/31、`不要输出解释性废话` 1/31、`不使用 Markdown 或任何加粗、斜体` 5/31。

| 护栏 | 原文（可直接抄） | 证据 |
|---|---|---|
| 禁散文/前言 | `请严格按照以下格式输出，精简中文，不要输出任何引言或解释：` | `tpl_10` `tpl_15` `tpl_20` `tpl_23` `tpl_60` `tpl_68` |
| 禁解释性废话 | `不要输出解释性废话，只要输出一段中文口播内容` | `tpl_129` |
| 禁 Markdown | `注意：不使用 Markdown 或任何加粗、斜体。` | `tpl_11` 的 5 个文案节点全带此句 |
| 禁解释（输出段） | `**输出：**仅中文提示词，不要输出任何引言或解释：` | `tpl_61` |
| 禁解释（提示词类） | `请直接输出一段完整的中文提示词，不要输出任何解释性话语` | `tpl_33` |
| 禁占位符 | `不出现 {占位符} 或 【】（仅用于说明）`、`不可出现占位符说明` | `tpl_20` `tpl_23` |
| 字数上限 | `字数不超过300字`、`提供10个爆款选题，字数不超过8字` | `tpl_11` |
| 禁画面文字 | `不允许出现任何文字元素（标题、文案、贴纸、英文单词等）` | `tpl_20` |

**重要实测提醒：护栏句式不是充分条件。** `tpl_11` 的 5 个文案节点都写了「不使用 Markdown 或任何加粗、斜体」，但 `data.value` 里仍出现了 `**【情感治愈类】**`、`**独处时的治愈感**`、emoji 与 `#话题标签`。所以：

- 护栏要写，但**不要承诺「输出一定干净」**；
- 对格式要求高的场景，用 **T2 自己写死**，或在下游提示词里加一道「忽略上游文本中的任何标记符号，只取内容」的兜底；
- 交付时如实说明「文本内容以画布实际结果为准，如需调整可在画布上直接用 `changes.text` 覆盖」。

## 6. 长度与结构建议

| 项 | 实测/建议 |
|---|---|
| LLM 指令长度 | 模板中位 **410 字**（均值 630，最大 4398）。**300–800 字是甜点区**；超过 1200 字只有 `tpl_82`（九宫格 JSON 分镜）这类强结构任务出现过 |
| 产出文本长度 | `value` 中位 146 字；套图类产出 341–428 字（4 段 × 约 60–110 字） |
| 分段方式 | 短指令用 `1. 2. 3.` 编号列表（`tpl_10` `tpl_32`）；长指令用 `## 标题` 分节（`tpl_15` `tpl_23` `tpl_33`）；紧凑型用 `**角色：**/**任务：**/**要求：**/**输出：**` 四行（`tpl_61`，288 字做到 6 段骨架） |
| 模板变量 | `tpl_32` 用 `{色调}` `{风格}` 花括号占位，并在 `# Constraints` 里写明「如无填写则…」的兜底；**agent 写 T1 指令时也应给兜底**，因为用户填的输入可能是空的 |

写作顺序建议：先写 `## 输出格式约束`（因为它决定产出能不能被下游切片），再倒推 `## 差异化维度`（N 路怎么变），最后补 `# Role` 和润色 `## 核心约束`。

## 7. 指令自检清单（写完逐条过）

1. 任务目标里写了**数量**（几张/几组/几段）。
2. 有上游输入时，明确说了「参考图1 / 参考图2 各是什么」，并规定了指代方式（`直接用"模特"和"产品"描述`）。
3. 核心约束覆盖三类：必须继承什么 / 严禁什么 / 缺信息时怎么办。
4. N>1 时写了差异化维度，且每个维度给了**可选值清单**。
5. 输出格式段有：锚点标记（逐字可对齐）+ 每段填写说明 + 段数 = 下游节点数。
6. 有护栏句：精简中文 + 不要输出任何引言或解释 + 不用 Markdown（对文案类再加字数上限）。
7. 指令长度落在 300–800 字，没有把整篇业务背景塞进去。
8. 该节点在计划里是 T1（`textMode:"llm"` + `manualSteps` 一条）还是 T2（`textMode:"copy"` + `text` 直接写死），**没有两头都写**。
9. 上游图/文节点在 `runs` 之前就已存在（T1）；或正文已写死（T2）。
10. 没有试图给文本节点写 `params.model`，也没有把文本节点放进 `runs`。

## 8. 文本模型选型（**作为交付物交给用户**）

硬件约束再强调一次：**文本节点的模型只能在画布 UI 选**（agent 写 `changes.params.model` → `INVALID_ARGUMENT`；`configure` → `UNSUPPORTED_NODE`）。所以技能的正确做法是：**在交付说明里给出「建议模型 + 理由 + 备选」**，让用户一次选对，而不是让他自己试。

目录共 9 个文本模型，**完整表 + 8 类任务的选型建议 + 交付话术模板见 `references/models-and-params.md` §8**。这里只留一句速记：

> **要读参考图再写 → `gemini-3.1-pro-preview`（也是当前默认，新代模板 8/8 都用它）；长文案/详情页 → `qwen3.7-max`；多风格文案 fan-out → `doubao-seed-2-0-pro-260215`；只做格式转换想更快 → `gemini-3.1-flash-lite-preview`。**

交付时把话术写成用户能照做的三句：**① 这个节点是文本节点，模型需要你在画布上选一次；② 建议选 X（理由一句）；③ 选好后点一次「生成」，产物落在这个节点的正文里，再运行下游出图节点。**

**不要做的事**：不要承诺「我帮你把模型配好了」；不要在计划里写 `params.model`；不要把文本节点放进 `runs`（§1、`references/models-and-params.md` §6）。
